    Git Fundamentals

    Day 01 What is Git :: Snapshot Model

    Git doesn't store a running list of diffs the way older systems did; it stores a full snapshot of the entire project at every commit, then optimizes storage by referencing unchanged files rather than copying them. Each commit points backward to its parent, forming a chain, or more precisely a directed graph, that traces the ship's exact configuration at any point in its history. This snapshot model is why Git can jump instantly to any past state: it isn't replaying changes, it's simply loading a stored image of that moment. Understanding this model reframes everything that follows, branches, merges, and rebases are all just different ways of navigating this graph of snapshots.

    Day 02 Basic Commands :: Init, Add, Commit

    Three commands form the core rhythm of daily operations aboard this ship: git init creates the repository, git add stages changes into the index, a holding bay before permanent recording, and git commit seals those staged changes into a permanent snapshot with a message describing the mission log entry. Staging is deliberate: you choose exactly which changes join the next commit, rather than committing everything indiscriminately. A clear, descriptive commit message is a log entry future crew members, including your future self, will depend on to understand why a change was made. We drilled this cycle, edit, stage, commit, until it became second nature.

    Day 03 Viewing History :: Log & Diff

    git log unspools the ship's full mission history, commit by commit, showing author, timestamp, and message for every recorded snapshot back to the very first. Flags like --oneline compress this into a scannable manifest, while --graph renders the branching structure visually, showing exactly where the ship's timeline split and rejoined. git diff shows the precise delta between two states, the exact lines added or removed, letting the crew inspect a change before committing it or review what happened between any two points in history. Together, these two instruments turn an opaque history into a fully navigable, inspectable record.

    Day 04 Undoing Changes :: Reset & Revert

    Mistakes happen even on a well-run ship, so Git gives us two very different tools for undoing them. git reset rewrites history, moving the branch pointer backward and optionally discarding changes, powerful but dangerous on anything already shared with the rest of the crew. git revert instead creates a brand new commit that undoes a previous one, preserving the full historical record rather than erasing it, the safer choice once work has left your local station. Choosing between them comes down to one question: has this history already been transmitted to other crew members?

    Day 05 Working with Remotes :: Clone & Push

    A remote is another ship's copy of the repository, typically a central hub like a shared station orbiting above the whole mission. git clone pulls down a complete copy of that remote repository, history and all, giving the new crew member a fully independent working copy. git push transmits your local commits up to the remote, synchronizing your work with the rest of the fleet, while git pull pulls their commits back down into yours. Working with remotes turns Git from a personal logbook into a coordinated communication system across the entire crew.

    STATUS: SECTOR_01_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 06 Ignoring Files :: .gitignore

    Not everything in a ship's working directory belongs in the permanent record: build artifacts, dependency caches, and local configuration files would only clutter the mission log with noise. A .gitignore file lists patterns Git should never track, keeping compiled output, node_modules, and secret credentials out of every future commit entirely. Ignoring a file only prevents new tracking; a file already committed keeps showing up until it's explicitly removed from the index with git rm --cached. A clean .gitignore, curated early, keeps the ship's history focused on what actually matters: source code and intent.

    Entering Sector 2

    Branching & Merging

    Day 08 Branching :: Isolated Development

    A branch is a lightweight, movable pointer to a commit, letting a crew member develop a new feature in complete isolation without disturbing the ship's main trajectory. git branch creates one, git switch or git checkout moves between them, and because branches are so cheap to create, Git encourages branching liberally for every distinct unit of work. Work committed on a feature branch doesn't touch the main branch at all until it's explicitly merged back in, so experimental work can be abandoned entirely with zero risk to the stable trajectory. This isolation is what makes parallel, concurrent development across a large crew possible without constant collision.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 09 Merging :: Integrating Changes

    Merging brings the work from an isolated branch back into the main trajectory, combining two divergent histories into one unified timeline. A fast-forward merge simply moves the pointer forward when no divergent work exists on the target branch, while a true merge commit creates a new snapshot with two parents, recording the exact point where two paths of development rejoined. git merge performs this operation, and understanding which type of merge is happening, fast-forward or true merge, explains why some histories stay linear while others show visible branching structure. Merging is the moment isolated work rejoins the shared mission record.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 10 Merge Conflicts :: Resolution

    A merge conflict occurs when two branches have changed the exact same lines of a file in incompatible ways, and Git, refusing to guess which version is correct, halts the merge and asks the crew to decide. Conflict markers, <<<<<<<, =======, and >>>>>>>, appear directly in the file, showing both competing versions side by side for manual review. Resolving a conflict means editing the file to the correct final state, removing the markers entirely, then staging and committing the result to complete the merge. Conflicts aren't malfunctions; they're Git correctly refusing to make a decision that requires human judgment about the ship's actual intent.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 11 Branch Strategies :: Git Flow

    As a crew scales up, ad hoc branching stops being enough, and structured branching strategies like Git Flow define exactly which branches exist and how work flows between them. Git Flow typically maintains a main branch for stable releases, a develop branch for integrated work in progress, and short-lived feature, release, and hotfix branches that merge back into both. Simpler strategies like GitHub Flow strip this down to just main plus feature branches merged through pull requests, favoring speed over ceremony for teams shipping continuously. Choosing a strategy is choosing a shared protocol the entire crew commits to following, consistency matters more than which specific strategy is picked.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 12 Rebase :: Clean History

    Rebasing rewrites a branch's history by replaying its commits on top of a new base, producing a linear history as if the work had been built there from the start, rather than the criss-crossing structure a merge commit leaves behind. git rebase main takes your feature branch's commits and reapplies them one by one onto the tip of main, generating new commit hashes for each one in the process. This produces a cleaner, easier-to-read log, but the golden rule stands firm: never rebase commits that have already been pushed and shared, since rewriting shared history strands every other crew member's copy. Rebase before sharing, merge after, is the safe rhythm most crews adopt.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 13 Cherry-Pick :: Selective Commits

    Sometimes only a single commit from another branch is needed, not the entire branch, and git cherry-pick lets the crew apply that one specific snapshot's changes onto the current branch without pulling in anything else. This is the standard tool for backporting a critical bug fix from the main development line onto an older stable release branch, where merging the entire branch would pull in unrelated, unready work. Cherry-picking creates a brand new commit with a new hash, even though the change is identical, since it's being replayed in a different historical context. Used sparingly, cherry-pick is precise surgery; used constantly, it signals a branching strategy that needs rethinking.

Each tool solves a distinct problem, and knowing which one the situation calls for is the actual skill, not memorizing commands in isolation.     Entering Sector 3

    Collaboration Workflows

    Day 15 Forking Workflow :: Open Source

    A fork is a complete, independent copy of someone else's repository, hosted under your own account, giving you full write access to your copy while the original project remains untouched until you explicitly propose changes. This is the standard workflow for open source contribution: fork the project, clone your fork locally, commit your changes on a branch, then push to your fork and open a pull request against the original repository. Keeping your fork synchronized with the upstream project, by adding it as a remote and periodically merging or rebasing, prevents your contribution from drifting too far out of date to merge cleanly. The forking model lets thousands of independent crews contribute to a single shared mission without needing direct write access to it.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 16 Feature Branch Workflow :: Teams

    Inside a single shared repository, most teams adopt the feature branch workflow: every unit of work, however small, gets its own short-lived branch cut from main, developed in isolation, then merged back through review. Branch names typically encode intent and ownership, like feature/telemetry-dashboard or fix/airlock-timeout, so any crew member can understand a branch's purpose at a glance without reading its full history. Keeping feature branches short-lived, merged within days rather than weeks, minimizes the painful conflicts that accumulate when a branch drifts too far from main's ongoing changes. This workflow is the connective tissue that lets many crew members build simultaneously without stepping on each other's work.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 17 Pull Requests :: Code Review

    A pull request is a formal proposal to merge one branch into another, bundling a diff, a description of intent, and a space for the rest of the crew to review before the change is accepted into the mission record. It's a checkpoint, not just a mechanical merge, catching bugs, design issues, and knowledge gaps before they reach the main trajectory, while simultaneously spreading understanding of the change across more than one crew member's head. Automated checks, tests, linters, and build verification, typically run against every pull request, blocking the merge until the ship's systems confirm the change is safe. A pull request left open too long accumulates drift and conflict, so healthy crews review and merge promptly rather than letting proposals stack up in orbit.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 18 Code Review Best Practices :: Feedback

    Reviewing a crewmate's pull request well is its own discipline: focus feedback on the code's actual behavior and clarity, not the author's competence, and always explain the reasoning behind a requested change rather than issuing bare commands. Small, focused pull requests are far easier to review thoroughly than sprawling ones, a five-hundred-line diff invites rubber-stamp approval where a fifty-line diff invites genuine scrutiny. Distinguishing blocking issues from optional suggestions, often with explicit labels, respects the author's time and keeps review from stalling the mission unnecessarily. Good review culture treats feedback as a gift exchanged between crew members working toward the same destination, not a gatekeeping ritual.

    Day 19 Tags & Releases :: Versioning

    A tag is a fixed, permanent pointer to a specific commit, unlike a branch which keeps moving forward, marking an exact point in history as significant, typically a release ready to leave the ship. git tag v1.2.0 stamps that commit permanently, and semantic versioning, major.minor.patch, communicates the nature of each release: breaking changes, new features, or bug fixes respectively. Annotated tags carry a message, author, and timestamp of their own, distinct from the commit they point to, making them suitable for formal release records rather than lightweight bookmarks. Pairing tags with generated release notes gives the rest of the fleet a clear, versioned map of exactly what shipped and when.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 20 Git Hooks :: Automation

    A Git hook is a script that fires automatically at specific points in the commit or push lifecycle, letting the ship enforce rules without relying on crew members to remember them manually. A pre-commit hook can run linters or tests before a commit is even allowed to complete, catching broken code before it enters the permanent record rather than after. A pre-push hook can block a push entirely if tests fail locally, and server-side hooks on the remote can enforce policy, like blocking direct pushes to main, for the entire crew at once. Hooks turn discipline that would otherwise depend on memory into discipline enforced automatically by the ship's own systems.

    Entering Sector 4

    Advanced Git

    Day 22 Stashing :: Temporary Changes

    Sometimes the ship needs an urgent course correction mid-task, before the current work is ready to commit, and git stash lets the crew shelve those uncommitted changes temporarily, returning the working directory to a clean state instantly. The stash acts as a stack, git stash pop restores the most recent shelved changes, while git stash list reveals everything currently held in reserve. This is the standard tool for context-switching without polluting history with half-finished, non-functional commits made only to save your place. Stashing lets a crew member respond to an emergency without losing a single line of the work already in progress.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 23 Interactive Rebase :: Squashing

    Interactive rebase, git rebase -i, opens an editable list of commits and lets the crew reorder, edit, combine, or drop them before they're shared with the rest of the fleet, essentially rewriting a messy work-in-progress log into a coherent narrative. Squashing folds several small, noisy commits, fix typo, fix typo again, actually fix typo, into one clean commit that tells a clear story about what changed and why. This is powerful precisely because it's dangerous: interactive rebase must only touch commits that haven't yet been pushed and shared, for the same reason regular rebase carries that rule. Used well, interactive rebase turns a chaotic personal history into a mission log the rest of the crew can actually learn from.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 24 Bisect :: Finding Bugs

    When a bug appears somewhere in a long history and nobody remembers exactly which commit introduced it, git bisect automates the search using binary search across the commit timeline. You mark one known-good commit and one known-bad commit, and Git checks out the midpoint for you to test, narrowing the search by half with every round until the exact culprit commit is isolated. This turns what could be hours of manual archaeology through hundreds of commits into a handful of test cycles, typically log-base-two of the total commit count. Bisect is one of Git's most underused instruments, precise, fast, and far more reliable than guessing where a regression was introduced.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 25 Submodules :: Nested Repos

    A submodule embeds one Git repository inside another as a fixed reference to a specific commit, useful when a ship depends on an external library or shared component that lives in its own independent history. git submodule add links the external repository at a specific path, but the parent repository only records which commit of the submodule to use, not the submodule's actual file contents directly. This means cloning a repository with submodules requires an extra step, git submodule update --init, or the linked directories arrive empty, a common source of confusion for new crew members. Submodules are powerful for sharing code across projects but add real operational complexity, and many crews now prefer simpler alternatives like package managers where the use case allows it.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 26 Advanced Config :: Aliases & Tricks

    Git's behavior is deeply configurable through git config, and defining aliases for frequently typed command sequences saves the crew enormous keystrokes over a long mission: git config --global alias.co checkout, or a more elaborate alias for a decorated, graphed log view. Global config in ~/.gitconfig applies across every repository on the ship, while local, per-repository config in .git/config overrides it for special cases, like a different author identity for a specific mission. Beyond aliases, config controls core behavior: default branch names, merge strategies, credential storage, and line-ending handling across different operating systems. A well-tuned config file is a personalized cockpit, built to match the exact rhythms of how one crew member actually works.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 27 Git Internals :: Objects & References

    Beneath every command lies a remarkably simple object model: Git stores everything as one of four object types, blobs holding file content, trees holding directory structure, commits holding snapshots, and tags holding named pointers, each addressed by the SHA-1 or SHA-256 hash of its own content. A commit object doesn't store a diff at all; it points to a tree representing the entire project state and to its parent commit, confirming the snapshot model from the very first day of this voyage. References, branches and tags, are nothing more than files in .git/refs containing a commit hash, which is why creating or moving a branch is nearly instantaneous, no data is copied, only a pointer moves. Understanding this internal model demystifies everything Git does above it; there is no magic left, only content-addressed storage and pointers.

    Day 28 Review :: Advanced Git

    This final review cycle traced the full arc from the snapshot model through branching and merging, collaborative workflows, and the advanced instruments, stashing, interactive rebase, bisect, submodules, custom configuration, and the raw object model underneath it all. Every layer depends on the ones beneath it; interactive rebase makes no sense without first understanding commits as snapshots, and bisect is only fast because the commit graph it searches is cheap to traverse. The crew demonstrated fluency across the full spectrum, from a first git init to confidently rewriting history before sharing it with the fleet.
