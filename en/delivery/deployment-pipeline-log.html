    The Conveyor

    Day 00 The Conveyor :: Initiation

    Today we stepped onto the Conveyor, the automated belt that carries code from a developer's hands to a running system. A deployment pipeline is a sequence of automated stages that build, verify, and release software without manual repetition of the same tedious steps. Understanding this conveyor is essential before we start loading cargo onto it, since a single misconfigured stage can jam the entire line. We toured the full length of the belt today, naming each station we will study in depth.

    Pipeline Fundamentals

    Day 01 What is a Pipeline :: Stages Overview

    We examined what a pipeline actually is: a defined sequence of stages, typically source, build, test, package, and deploy, each gating entry into the next. Failure at any stage halts the conveyor immediately, preventing broken cargo from reaching later, more expensive stations. This fail-fast principle saves enormous time compared to discovering a defect only after full deployment. We diagrammed a basic five-stage pipeline today and traced how a single commit flows through it.

    Day 02 Source Control :: Triggering Builds

    Today's lesson covered how a pipeline is triggered from source control, watching a repository for pushes, tags, or pull requests that should ignite the conveyor. Webhooks notify the pipeline system the instant new code lands, removing the need for manual polling or human initiation. Configuring trigger rules carefully prevents wasted runs on irrelevant branches while ensuring nothing important slips through unbuilt. We configured a trigger today that fires only on pushes to protected branches.

    Day 03 Build Stage :: Compilation

    We studied the build stage, where source code is compiled, transpiled, or bundled into a runnable artifact. This station converts human-readable instructions into the binary or packaged form a machine can actually execute, catching syntax errors and missing dependencies immediately. A clean, reproducible build environment is essential, since a build that only works on one engineer's machine defeats the purpose of automation. We ran our first automated build today, watching the conveyor reject a deliberately broken syntax error.

    Day 04 Test Stage :: Automated Checks

    Today we reached the test stage, where automated suites verify that new code behaves as expected before it travels further down the line. Unit tests check individual components in isolation, while integration tests confirm that assembled parts still function together correctly. A pipeline that skips this station risks shipping defects directly to passengers, so most conveyors refuse to advance cargo that fails here. We wired a test suite into our pipeline today and watched it correctly block a regression.

    Day 05 Package Stage :: Artifacts

    We covered the package stage today, where verified code is bundled into a distributable artifact such as a container image, a compiled binary, or a versioned archive. Packaging standardizes what actually gets deployed, ensuring the exact bits tested in the previous stage are the same bits that ship, with no last-minute edits introducing drift. Artifacts are typically tagged with a version or commit hash so any deployed instance can be traced back to its origin. We built and tagged our first container image today as part of this stage.

    Day 06 Deploy Stage :: Release

    Today we arrived at the deploy stage, the final station where packaged artifacts are released into a live environment. This can mean pushing a container to a cluster, uploading a binary to a server fleet, or publishing static files to a hosting platform. Automated deploys remove the error-prone ritual of manual file copying, replacing it with a repeatable, auditable action. We simulated a deploy to a test environment today, confirming the artifact from the package stage arrived intact.

    Day 08 GitHub Actions :: Workflow Setup

    Today we configured our first real workflow setup in GitHub Actions, translating the pipeline theory into an actual YAML definition. Jobs and steps map directly onto the stages we studied, with each job running on a fresh virtual runner unless explicitly cached or chained. We wrote a workflow file today with distinct jobs for build, test, and deploy, wiring dependencies between them so later jobs wait for earlier ones to succeed.     Day 09 Jenkins :: Self-Hosted CI

    We examined Jenkins today, the long-standing self-hosted automation server that many older fleets still rely on. Unlike hosted platforms, Jenkins requires a crew to provision and maintain its own runner infrastructure, trading convenience for full control over the execution environment. Pipelines are defined in a Jenkinsfile using a Groovy-based DSL, describing stages much like the ones we've already studied. We installed a local Jenkins instance today and ran a simple declarative pipeline against it.

    Day 10 GitLab CI :: Integrated Pipelines

    Today's lesson covered GitLab CI, a pipeline system integrated directly into the GitLab platform rather than bolted on separately. Pipelines are defined in a .gitlab-ci.yml file at the repository root, describing stages and jobs in a structure similar to what we've seen elsewhere. GitLab's tight integration means merge requests, pipeline status, and deployment environments all appear in one unified interface. We configured a basic GitLab CI pipeline today and observed its stage graph render automatically.

    Day 11 Environment Variables :: Pipeline Config

    We studied environment variables and pipeline configuration today, the mechanism for injecting settings and secrets into a running job without hardcoding them into scripts. Variables can be scoped globally, per pipeline, or per environment, letting the same pipeline definition behave differently for staging versus production targets. Sensitive values should always be marked as protected or masked so they never appear in logs. We configured a set of environment-specific variables today and verified they resolved correctly per target.

    Day 12 Caching in CI :: Speed Optimization

    Today we tackled caching in CI, a technique for avoiding redundant work across pipeline runs. Dependency directories, compiled build artifacts, and downloaded packages can be cached between runs, dramatically reducing the time spent on repeated installation steps. A poorly configured cache can serve stale data, so cache keys must be tied to the inputs that actually determine validity, like a lockfile hash. We measured our pipeline's runtime before and after enabling caching today, observing a significant speedup.

    Day 13 Parallel Jobs :: Faster Pipelines

    We explored parallel jobs today, running independent pipeline stages simultaneously on separate runners rather than sequentially. Tests that don't depend on each other, or builds targeting different platforms, are ideal candidates for this kind of fan-out. Parallelization can cut total pipeline duration dramatically, though it requires runners with sufficient capacity and careful dependency management to avoid races. We split our test suite into three parallel jobs today, cutting total pipeline time nearly in half.

    CD Implementation

    Day 15 Continuous Deployment :: Auto Release

    Today we crossed into continuous deployment, where every change that passes the pipeline is released automatically without a manual approval gate. This represents the fastest possible cycle from commit to production, appropriate for teams with strong automated test coverage and confidence in their safety nets. Without adequate testing, continuous deployment can ship defects to users at the same speed it ships fixes. We configured a fully automated deploy today, watching a passing pipeline release directly to a live target.

    Day 16 Staging Environments :: Pre-Prod

    We studied staging environments today, the pre-production waypoint that mirrors live conditions as closely as possible without exposing real passengers to risk. A staging deploy lets the crew verify behavior under realistic load, configuration, and data shape before committing to a full production release. Discrepancies between staging and production, sometimes called environment drift, are a common source of surprises that this stage exists to catch. We deployed to a staging environment today and compared its configuration against production for drift.

    Day 17 Blue-Green Deployments :: Zero Downtime

    Today's lesson covered blue-green deployments, a strategy for achieving zero downtime by running two identical production environments and switching traffic between them. The blue environment serves live traffic while green receives the new release, and once green is verified, a router or load balancer flips traffic over instantly. If problems emerge, reverting is as simple as flipping the switch back to blue. We simulated a blue-green cutover today, verifying that traffic switched without any dropped requests.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 18 Canary Releases :: Gradual Rollout

    We examined canary releases today, a gradual rollout strategy that exposes a new version to a small percentage of traffic before a full release. Monitoring error rates and latency on the canary slice reveals problems while exposure is still limited, protecting the majority of passengers from broader impact. If the canary performs well, traffic is incrementally shifted until the new version handles everything. We configured a canary rollout today, watching traffic ramp from five percent up to full deployment.

    Day 19 Feature Flags :: Toggle Features

    Today we studied feature flags, runtime toggles that separate deploying code from releasing functionality to users. A feature can be deployed dark, meaning the code ships to production but remains inactive until a flag is flipped, decoupling release risk from deployment risk entirely. Flags also enable targeted rollouts to specific user segments and instant rollback without a redeploy. We wired a feature flag into a sample application today and toggled it live without touching the deployment pipeline.

    Day 20 Rollback Strategies :: Safe Reverts

    We covered rollback strategies today, the procedures for safely reverting a bad deployment before it causes lasting damage. Options include redeploying a previous known-good artifact, reverting the triggering commit, or toggling a feature flag off if one gates the new behavior. A good rollback strategy is rehearsed in advance and measured for speed, since the value of a rollback plan is inversely proportional to how long it takes to execute under pressure. We ran a rollback drill today, timing how quickly we could restore the previous stable version.

    Pipeline Best Practices

    Day 22 Pipeline Security :: Secrets Management

    Today we addressed pipeline security, focusing on how secrets like API keys and deployment credentials are managed without leaking into logs or source history. Secrets should be injected at runtime from a dedicated vault or the platform's secret store, never hardcoded into pipeline definitions or committed to the repository. Least-privilege access ensures a compromised pipeline credential can't reach further than its specific job requires. We audited a sample pipeline today and found two hardcoded values that should have been secrets.

    Day 23 Pipeline Monitoring :: Visibility

    We studied pipeline monitoring today, the instrumentation that gives a crew visibility into how the conveyor is performing over time. Dashboards tracking build duration, failure rate, and deployment frequency reveal degrading health long before a full outage occurs. Alerting on anomalies, such as a sudden spike in build failures, lets the crew respond before a minor issue compounds.     Day 24 Pipeline as Code :: Versioned Config

    Today's lesson covered pipeline as code, the practice of defining the entire pipeline configuration in version-controlled files rather than through a mutable web interface. This means pipeline changes go through the same review process as application code, with history, diffs, and rollback available for the automation itself. It also makes pipelines portable and reproducible across environments, since the configuration travels with the repository. We migrated a manually configured pipeline into version-controlled YAML today.

    Day 25 Multi-Environment Pipelines :: Dev/Stage/Prod

    We examined multi-environment pipelines today, structures that promote a single artifact progressively through development, staging, and production without rebuilding it at each step. Building once and promoting the same artifact guarantees that what was tested is exactly what ships, eliminating a whole class of environment-specific build discrepancies. Each promotion gate can require different approvals or automated checks appropriate to that environment's risk level. We configured a three-environment promotion chain today, tracing one artifact from build through to production.

    Day 26 Pipeline Testing :: Testing the Pipeline

    Today we studied pipeline testing, the practice of verifying that the pipeline definition itself behaves correctly, not just the application it builds. This can include linting workflow syntax, running the pipeline against a mock repository, or asserting that specific stages fail under known bad conditions. Treating pipeline code with the same rigor as application code catches misconfigurations before they cause a failed release at the worst possible moment. We wrote a test today that verified our deploy stage correctly refuses to run if the test stage failed.

    We covered pipeline documentation and runbooks today, the written procedures that let any crew member operate or troubleshoot the conveyor without tribal knowledge. A good runbook explains how to trigger a manual deploy, how to perform a rollback, and who to contact when a stage fails mysteriously. Documentation that lives next to the pipeline code, rather than in a separate forgotten location, is far more likely to stay accurate.
