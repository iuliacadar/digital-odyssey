    The GitHub Expedition

    Charting the principles, patterns, and practices of GitHub.

    ENTER AIRLOCK

    The Hub

    Day 00 The Hub :: Initiation

    Today the crew boarded the Hub, the great orbital station where every voyage of code begins. GitHub is not merely a parking bay for repositories; it is a coordination platform where version history, collaboration, and deployment converge into a single command deck. Before any expedition launches, cadets must understand that this station tracks every commit as a permanent log entry, immutable once written. Learning to navigate its interface is the first step toward disciplined, traceable engineering.

    GitHub Fundamentals

    Day 01 GitHub Overview :: Platform Basics

    We surveyed the platform's core instrumentation today. GitHub layers a social and organizational shell around the raw Git engine: repositories, organizations, teams, and permissions all live here as visible structures on the station's hull. Stars, forks, and watch counts function like sensor pings, telling us how much attention a given vessel draws from the wider fleet. Grasping this basic topology lets a navigator find their bearings before touching any deeper system.

    Day 02 Repositories :: Structure & Settings

    Attention turned to the repository itself, the pressurized module where a project's contents actually live. Each repo carries settings for visibility, branch protection, and default branches, all of which determine how safely code can be modified without risking hull breach. We configured a fresh repository, setting its default branch and reviewing the topics and description fields that help other crews discover it. A well-structured repository is the difference between an orderly cargo hold and scattered debris.

    Day 03 README & Wikis :: Documentation

    Today's lesson concerned the README file and the wiki, the documentation beacons that guide any boarding crew. A README rendered at the root of a repository is the first transmission a visitor receives, so it must explain purpose, installation, and usage clearly and quickly. Wikis extend this further, offering a deeper knowledge base for architecture notes, decision logs, and onboarding guides that don't belong in the main transmission. Cadets practiced writing Markdown headers, code fences, and badges to make their documentation legible at a glance.

    Day 04 Issues :: Tracking Work

    We opened the Issues bay, the station's system for tracking anomalies, requests, and pending work. Every issue is a ticket logged against the mission, complete with a title, description, and thread of discussion where crew members can debate the best fix. Filtering by open, closed, or assignee lets a team commander triage the queue quickly during a long voyage. Cadets filed their first issues today, learning to write reproducible steps so future readers understand the anomaly without guesswork.

    STATUS: SECTOR_01_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 05 Labels & Milestones :: Organization

    Today we organized the issue queue using labels and milestones, the tagging and grouping tools that keep a growing backlog from becoming chaotic drift. Labels like bug, enhancement, and priority act as colored flags on the hull, letting the crew scan hundreds of tickets at a glance. Milestones bundle issues and pull requests into a shared deadline, useful for tracking progress toward a release checkpoint. Applying both consistently is what separates an organized expedition log from an unreadable mess of transmissions.

    STATUS: SECTOR_01_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 06 Projects :: Kanban Boards

    Attention shifted to Projects, GitHub's kanban board for visualizing the flow of work across the mission. Cards representing issues and pull requests move through columns such as backlog, in progress, and done, giving the whole crew a shared view of the mission's state. Automation rules can move cards automatically when a linked pull request merges, reducing manual bookkeeping. We built our first board today, mapping the coming sprint's tasks onto a visible pipeline.

    Day 07 Review :: GitHub Fundamentals

    Review day. We revisited the fundamentals: the Hub as coordination platform, repositories as the pressurized modules holding our code, README files as first-contact beacons, and issues, labels, milestones, and projects as the instruments for tracking and organizing work. A crew that has internalized these basics can move confidently into the deeper collaboration mechanics ahead.     Entering Sector 2

    Pull Requests & Review

    Day 08 Creating PRs :: Process

    Today we launched our first pull request, the formal mechanism for proposing that a branch's changes be merged into the mainline. A PR bundles a diff, a description, and a conversation thread, transforming a private branch into a public proposal the whole crew can inspect. We practiced writing clear PR descriptions that explain what changed and why, since a reviewer without context is like a technician reading unlabeled wiring. Understanding this process is the gateway to every collaborative contribution that follows.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 09 Reviewing Code :: Comments & Suggestions

    We drilled the art of code review today, learning to leave line-level comments and suggested changes directly on a diff. A good review comment identifies a specific risk or improvement rather than a vague objection, and the suggestion feature lets a reviewer propose an exact replacement the author can accept with one click. Cadets practiced both giving and receiving feedback, since a healthy review culture treats critique as hull maintenance, not personal attack. This discipline is what keeps a shared codebase structurally sound over many voyages.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 10 CI Integration :: Actions Checks

    Today's systems check involved CI integration, watching automated status checks report directly on the pull request. Every push to a PR branch can trigger a workflow that compiles, lints, and tests the code, posting green or red status markers before a human reviewer even looks. Branch protection rules can require these checks to pass before merge is allowed, acting as an automated airlock seal. We wired a simple check into a sample PR today and watched it block a deliberately broken build.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 11 Merge Strategies :: Squash & Rebase

    We studied the three merge strategies available at the airlock: merge commit, squash, and rebase. A standard merge commit preserves the full branch history, a squash merge collapses many small commits into one clean entry, and a rebase replays commits onto the tip of the target branch for a linear history. Each strategy trades off traceability against readability, and a team must agree on a convention before conflicting styles pollute the log. We practiced all three today on a controlled test repository.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 12 Draft PRs :: Work in Progress

    Today's focus was draft pull requests, a mode for signaling work still underway. Marking a PR as draft prevents accidental merging while still allowing early feedback and running CI checks against in-progress code. This is useful for long voyages where a crew member wants visibility into their trajectory before final review. We converted a draft to ready for review today, observing how the status change alerts assigned reviewers automatically.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 13 PR Templates :: Standardization

    We built a pull request template today, a standardized form that pre-populates new PRs with the same structure: summary, testing notes, and a checklist. Templates reduce the cognitive load on contributors and ensure reviewers always receive the context they need, much like a preflight checklist ensures no critical step is skipped before launch. Storing the template in the .github directory makes it apply automatically across the repository. Consistency here saves the crew from re-explaining the same missing details every voyage.

    STATUS: SECTOR_02_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 14 Review :: Pull Requests

    Review day for pull requests. We consolidated everything: opening a PR, writing reviews with inline comments and suggestions, wiring CI checks into the merge gate, choosing a merge strategy, using drafts for in-progress work, and templating the process for consistency. A crew fluent in this cycle can collaborate on code changes without stepping on each other's trajectories. Cadets completed a full simulated PR lifecycle today, from branch to merge.

    Entering Sector 3

    GitHub Actions & Automation

    Day 15 Actions Overview :: Workflows

    Today we opened the Actions bay, GitHub's built-in automation engine. A workflow is defined in YAML and triggered by events like pushes, pull requests, or schedules, then executes a sequence of jobs and steps on a virtual runner. This is the propulsion system behind continuous integration, turning manual verification rituals into automated, repeatable checks. We wrote our first workflow file today, triggering a simple script on every push to the main branch.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 16 Custom Actions :: Building

    We moved from consuming actions to building our own custom action today, a reusable unit of automation that can be shared across repositories. Actions can be composite scripts, Docker containers, or JavaScript modules, each packaged with metadata describing its inputs and outputs. Publishing a custom action to the marketplace lets other crews install it into their own workflows without duplicating logic. We authored a small composite action today that echoes a greeting using an input parameter.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 17 Scheduled Workflows :: Cron Jobs

    Today's lesson covered scheduled workflows, triggered not by an event but by a cron expression ticking on the station's internal clock. This is useful for periodic maintenance tasks like nightly builds, dependency audits, or cleanup jobs that don't depend on human activity. We configured a workflow to run daily at a fixed hour, verifying its execution in the Actions history log. Scheduled automation lets the crew rest while routine maintenance continues in the background.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 18 Environment Secrets :: Secure Variables

    We secured our automation today using environment secrets, encrypted variables that workflows can access without exposing sensitive values in plaintext. API keys, deployment tokens, and credentials belong here rather than in a workflow file, since anything committed to history is effectively public forever. Environments add an extra layer, letting secrets be scoped to specific deployment targets like staging or production. Cadets practiced referencing a secret safely within a workflow step today.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 19 Matrix Builds :: Multi-Config

    Today we ran matrix builds, a technique for testing a single codebase across multiple configurations simultaneously. A matrix might vary operating system, language version, or dependency set, generating a separate job for every combination automatically. This catches compatibility anomalies that a single fixed environment would never reveal, much like testing hull integrity across a range of atmospheric pressures. We configured a matrix spanning three runtime versions today and watched all three jobs execute in parallel.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 20 Deployment Actions :: Auto Deploy

    We wired up deployment actions today, automating the final push of verified code to a live environment. A deploy job typically runs only after build and test stages succeed, connecting to a hosting provider through an authenticated action step. This closes the loop from commit to production without manual intervention, though guardrails like required approvals keep a human in command of the final decision. We simulated a deployment today using a mock hosting target to observe the full sequence.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 21 Review :: Actions & Automation

    Review day for Actions and automation. We covered workflow syntax, building custom actions, scheduled triggers, secret management, matrix testing, and deployment automation. Together these form the propulsion and guidance systems that carry code changes from a developer's branch to a running service with minimal manual intervention. Cadets assembled a composite workflow today exercising every concept from this cycle in sequence.

    STATUS: SECTOR_03_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Entering Sector 4

    GitHub Ecosystem

    Day 22 GitHub Pages :: Static Sites

    Today we launched GitHub Pages, the built-in static site hosting attached to every repository. Pages serves HTML, CSS, and JavaScript files directly from a branch or a dedicated build artifact, giving any crew a free public terminal for documentation or a portfolio. We configured Pages to build from a specific branch today, watching it publish automatically after each push. This is often the fastest way to get static content in front of an audience without provisioning separate infrastructure.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 23 GitHub Packages :: Package Registry

    We explored GitHub Packages today, the platform's integrated registry for hosting compiled artifacts like container images, npm packages, or Maven builds. Publishing here keeps package distribution tied to the same permissions and organizational structure as the source repository, avoiding a separate trust boundary. We published a small test package today and pulled it back down to confirm the registry round-trip worked. This keeps supply chains short and auditable within a single platform.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 24 Dependabot :: Dependency Updates

    Today's system covered Dependabot, the automated sentinel that scans dependency manifests for outdated or vulnerable packages. When a newer or patched version exists, Dependabot opens a pull request automatically, complete with changelog links and compatibility notes. This offloads the tedious work of manual version tracking, letting the crew focus on reviewing rather than searching. We enabled Dependabot on a sample repository today and observed its first automated update proposal.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 25 Security Advisories :: Vulnerability Mgmt

    We studied security advisories today, the mechanism for privately disclosing and coordinating fixes for vulnerabilities before public release. A maintainer can draft an advisory, collaborate with reporters in a private fork, and publish a CVE-linked disclosure once a patch ships. This protects users from exposure during the vulnerable window while still crediting researchers who found the issue. Understanding this process matters for any crew maintaining a dependency others rely on.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 26 GitHub CLI :: Command Line

    Today we left the browser behind and worked entirely through the GitHub CLI, the command-line interface for repository operations. The gh tool lets a crew member create issues, open pull requests, and check workflow runs without leaving the terminal, folding station operations into the same shell used for local development. We practiced creating a pull request end-to-end from the command line today, from branch push to merge. This is often faster for crews who prefer to keep their hands on the keyboard rather than the mouse.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Day 27 GitHub API :: Automation

    We studied the GitHub API today, the programmatic interface underlying both the web interface and the CLI. REST and GraphQL endpoints expose nearly every platform capability, letting a crew build custom tooling, bots, or dashboards tailored to their mission. Authentication via personal access tokens or GitHub Apps controls what a script is permitted to touch. We wrote a small script today that queried open issues via the API and printed a summary report.

    STATUS: SECTOR_04_ACTIVE | RECEPTOR: ACTIVE | LINK: CONFIRMED

    Review day for the GitHub ecosystem. We closed the loop on Pages for hosting, Packages for distribution, Dependabot and advisories for security, and the CLI and API for automation beyond the browser. Together these extend the Hub from a mere code repository into a full mission control platform. Cadets completed a capstone exercise today, publishing a page, registering a package, and querying it all through the CLI.
